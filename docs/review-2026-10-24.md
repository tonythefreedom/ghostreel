## MCP 클라이언트 수정

복구 규칙은 2025-06-18 Streamable HTTP 스펙에 있습니다. 공식 SDK가 이미 이 규칙을 구현하고 있어서, 고치는 것보다 바꾸는 쪽이 더 쉬울 수 있습니다.

1. **`Mcp-Session-Id`와 함께 404:** 세션이 없어진 것입니다. 예전 id 없이 새로 `initialize`를 보내고, 결과를 확인하고, `notifications/initialized`를 보낸 뒤 새 id를 저장합니다.
2. **세션 id가 없다는 400:** id를 넘기는 부분을 고칩니다. 가진 id가 없으면 새로 initialize합니다. 다른 400(잘못된 프로토콜 버전, 잘못된 요청)은 세션 만료가 아니니, 횟수를 정해 두고만 재시도합니다.
3. **SSE:** 이벤트는 빈 줄에서 끝납니다. 한 이벤트 안의 여러 `data:` 줄은 줄바꿈으로 잇습니다. CR, LF, CRLF와 주석 줄을 처리하고, 알림이나 서버 요청이 아니라 `id`가 요청과 같은 JSON-RPC 응답을 고릅니다.
4. **헤더와 id:** initialize 뒤의 모든 요청에 `MCP-Protocol-Version`을 보냅니다. `InitializeResult`를 검증하고, 동시에 일어난 initialize는 하나로 합칩니다. 요청 id는 카운터로 만듭니다. `Date.now()`는 같은 밀리초 안에서 겹칩니다.
5. **부작용:** 애매한 타임아웃 뒤에 GPU 확인 요청을 무작정 다시 보내지 않습니다. 먼저 작업 상태를 확인합니다.

**brief 연결 (계획이며 측정한 것은 아님).** 정렬한 `lines[].say`를 하나의 take로 합치고, take와 create에 같은 문장을 씁니다. `scene`과 `outfit`은 keyframe 프롬프트로, `lines[].do`는 `motion_beats {entry, delivery, exit}`로 정리합니다. `do`는 이미 영어라 도구가 요구하는 형식과 맞습니다. 실제 TTS 길이를 재서 10초 또는 15초에 맞게 대본을 줄입니다. `finishBrief`는 타임스탬프만 다듬고 전체 말 길이는 제한하지 않습니다. 여러 클립을 붙이는 방식은 장면이 실제로 바뀔 때만 씁니다.

**승인.** GPU를 쓰는 단계는 모두 미리보기 다음 `confirm_token`으로 확인합니다. 우리 Approve 버튼은 CineSynth의 확인을 대신하지 않습니다. T11에서는 승인 한 번을 정확히 brief 하나에 묶고, 고치면 승인을 다시 받아야 합니다.

**확인되지 않은 것.** 서버 프로세스가 쓸 인증 정보, `confirm_token` 유효 시간, 실제 렌더 시간, 사용자별 하루 GPU 한도, 대기열 동작입니다. GPU 작업은 아직 한 번도 돌리지 않았습니다. 다음 단계는 승인받은 10초 샘플 1개를 단계별로 시간을 재며 렌더하는 것이고, 그 뒤에 H5까지 미리 렌더 3개를 약속할지 정합니다.

**대안.** 주인이 직접 운영하는 세션에서 렌더한 클립을 `public/prerender/`에 넣고, `provider: 'prerender'`, AI 표시, manifest(캐릭터, 승인한 대본, 길이, 출처)를 붙입니다. 고정 클립을 새 brief로 방금 렌더한 것처럼 보여 주지 않습니다.
